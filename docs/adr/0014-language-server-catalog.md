# 14. Language servers come from a signed catalog, installed by hand

**Status:** accepted, 2026-11-21

**Resolves:** D12 in `TODO.md`

**Relates to:** ADR 0003 (a static, signed extension index), ADR 0010 (install
provenance), ADR 0011 (release signatures), P7-3 (the registry that ships),
P7-12 (the trust pin)

## Context

P7-3 ships detection: four built-in presets, an `lsp.toml` a profile can edit,
and a status row that says what was found on `PATH` or what is missing. The
non-goal said the product would not download language servers, because a
language server is an arbitrary executable with the workspace and the network,
and an auto-download is a supply chain nobody reviewed.

The D12 answer reverses the non-goal but keeps the security property that made
it defensible: **no silent install**. Detection remains the default. A managed
install is an explicit act, from a signed catalog, with a checksum, a licence
and a pin, and it never happens during a keystroke or in the background.

Two questions had to be settled before code: whether this is v0.1 or v0.2, and
whether every server can be redistributed. The answer to the second is no, and
that shapes the catalog rather than being handled by a warning.

## Decision

### 1. v0.2, not v0.1

v0.1's definition of done says "the language servers you already use", which
detection satisfies. The catalog is a review process, a signing key, a download
path, archive handling on two platforms and a licence audit across roughly
thirty languages. None of it is needed to open a file in v0.1, and putting it in
v0.1 would make the release's supply chain the thing that slips.

v0.1 therefore ships P7-3 as it is, with the direction stated in the status
output and the docs. The downloader is a new P7 task after P7-13, scheduled for
v0.2.

### 2. The catalog is generated, reviewed, and signed

The source of truth is one human-maintained TOML file per server in
`lsp/<id>.toml`, reviewed in a pull request. `cargo xtask lsp-index` generates
`marketplace/lsp/index-v1.json` from them, and the release process signs the
generated bytes with a detached ed25519 signature, in the same
`<index>.json.sig` form the extension index uses (ADR 0003 §3): the signature
covers the exact bytes, so the digest cannot be swapped underneath it.

The public key ships in the binary as `ACPILOT_LSP_INDEX_PUBKEY`. It is a
separate key from the extension index and the release key: rotating the release
signing key must not invalidate a catalog, and a catalog review is a different
duty from cutting a release. A build without the key has no way to answer "who
published this" and refuses managed installs rather than falling back to a bare
checksum.

JSON rather than TOML for the generated artifact follows D23: TOML is for files
a person maintains, JSON for generated state and the wire. The reviewed input
stays TOML.

The index is served at
`https://rudeboy.dev/acpilot/lsp/index-v1.json`, with its `.sig` beside it. It is
a static document, not an API; a private mirror can be named with
`--lsp-index <url>` plus a trusted key, exactly as a private extension registry
works.

### 3. What an entry says

```json
{
  "schema_version": 1,
  "generated_at": "2026-11-21T00:00:00Z",
  "servers": [
    {
      "id": "rust-analyzer",
      "name": "rust-analyzer",
      "languages": ["rust"],
      "version": "2026-11-01",
      "license": "MIT OR Apache-2.0",
      "redistributable": true,
      "source": "https://github.com/rust-lang/rust-analyzer",
      "targets": {
        "x86_64-unknown-linux-gnu": {
          "url": "https://github.com/rust-lang/rust-analyzer/releases/download/2026-11-01/rust-analyzer-x86_64-unknown-linux-gnu.gz",
          "sha256": "…",
          "size": 18234221,
          "archive": "gz",
          "executable": "rust-analyzer"
        }
      }
    }
  ]
}
```

- `version` is the upstream release identifier, not a semver this project
  invents. Two servers with different version schemes are not compared.
- `targets` is keyed by the Rust target triple the release artifact is for. A
  target the daemon does not recognise means "not available here", not "try the
  nearest one".
- `archive` is `tar.gz`, `zip` or `gz` (a single compressed executable, which is
  how rust-analyzer and several Go servers ship).
- `executable` is a path inside the archive after stripping one top-level
  directory when `strip = 1` is present. It must be a regular file.
- `redistributable` is a reviewed fact, not a guess. Only `true` entries may
  carry a `url` the daemon will fetch.
- `yanked` may appear on a target or a version. A yanked version is refused at
  the next catalog read; the installed copy is not deleted behind the user's
  back.

### 4. Licence decides whether there is a download at all

The catalog includes a server only if its licence permits redistribution of the
binary the entry points at. That is a per-server review with the licence text
and the upstream release in front of the reviewer, not a field copied from the
repository's badge.

A server that cannot be redistributed is still *known*: it gets an entry with
`"redistributable": false`, no `url`, a `source` and an `install` hint (the
package name, or the upstream release page). `acpilot lsp status` shows it as
"found on PATH" or "not installed; see <hint>", and the daemon never fetches it.
Detection and trust-pinning work for it exactly as they do today.

This is why the catalog review is not a formality. A missing entry is a worse
outcome than a "no" with an explanation, because the explanation is what a
person can act on.

### 5. Install is an explicit, verified act

```
acpilot lsp install rust
acpilot lsp install rust@2026-11-01
acpilot lsp install --from ./rust-analyzer.gz --sha256 <digest>
```

The command resolves the language to a server and the host to a target, verifies
the catalog signature, then shows what it is about to do: server, version,
source URL, licence, download size and install path. `--yes` exists for scripts;
without it, a prompt defaults to no. A TUI "install" action runs the same code
and the same prompt — it is not a second downloader.

Verification order, before anything is extracted:

1. The catalog signature verifies against a trusted key.
2. The archive's SHA-256 and size match the entry (size also caps the read).
3. The URL is HTTPS; redirects to another scheme are refused.
4. The archive is one of the three supported shapes, by its bytes rather than
   its name.

Extraction rules are the extension loader's, restated because this is a second
caller: no absolute paths, no `..` component, no symlink or hardlink whose
target escapes the extraction root, no device or socket entries, one top-level
directory at most when `strip = 1`, and a total extracted size cap (default
512 MiB, from the catalog's declared size plus slack). A partial extraction is
removed; the install is either complete or absent.

The executable bit is set on the file the catalog names, `0755` on unix. Files
are written under `<data>/lsp/<id>/<version>/<target>/`, with a sibling
`install.json` recording the catalog URL and digest, the archive digest, the
executable digest, the source URL, the target and the installation time. The
install goes to a temporary directory in the same parent and is renamed into
place, so a crash leaves no half-server that looks installed.

No install happens in the background, on startup, or because a file was opened.
There is no auto-update channel. `acpilot lsp update` is a command, and a version
is never replaced while a server from it is running — the running process keeps
its bytes, and the next start uses the new directory.

### 6. The install is the trust decision; the pin still exists

P7-12 pins a language server's executable by SHA-256 and refuses to run it after
the bytes change. A managed install is already a person approving an exact
archive from a reviewed catalog, so the daemon records the executable's pin on
first use in a profile without a second prompt — but only when the executable
still hashes to the `install.json` value and that value is the one the install
verified. A changed file is `untrusted`, and untrusted means no server.

Detection is unchanged: a binary found on `PATH` is pinned the first time a
person approves it, and a changed binary prompts or refuses exactly as it does
today. The install path does not weaken the gate; it answers it in advance.

### 7. Resolution order

For a language, the daemon starts the first of:

1. A `command` written in the profile's `lsp.toml` (an explicit path or name).
2. A managed install for the version the profile pins.
3. The newest managed install that is not yanked.
4. A program found on `PATH`.

Explicit configuration wins because it is a person naming a program. A managed
install outranks `PATH` because installing one is the act that says "use this";
falling back to an unrelated `PATH` binary would silently ignore the artifact
that was verified. If the selected managed install is untrusted or yanked, the
daemon reports that and starts nothing — it does not quietly try the next row,
which would make the pin advisory.

`lsp.toml` keeps its shape and gains two keys:

```toml
[lsp.rust]
# command = "/opt/rust-analyzer"   # explicit, wins
version = "2026-11-01"              # pin a managed install
# args, initialization_options, settings, env unchanged
```

`acpilot lsp status` names the resolution: the program, whether it came from
`PATH`, a managed version or an explicit command, its trust state, and for a
missing server the exact install command for this host.

### 8. Catalog reads are deliberate and cached

The daemon fetches the catalog only for `lsp install`, `lsp update`, `lsp
search` and `lsp status --check`. It caches the verified bytes and signature
under `<data>/lsp/index.json` for 24 hours and re-verifies the signature on every
read. Nothing fetches at startup.

`--offline` uses the cached catalog, and an install from a cached catalog still
needs the archive; `--from` is the air-gapped path, with `--sha256` required
unless the file's digest matches a cached entry. A catalog that cannot be
fetched is not an error on a machine that already has servers: status says the
catalog is stale, and the installed copies keep working.

### 9. Remote hosts are not downloaders

A daemon serving a remote host refuses `lsp install` and prints the command to
run on that host. The server must execute where the files are; downloading on
the client and shipping a binary is a different, audited feature. The remote
status row is the host's answer, not the client's guess.

### 10. v0.1 behaviour does not change retroactively

Until the downloader exists, `lsp install` is not a command, `lsp status` says
the server is missing and names the detected alternative, and nothing in the
docs promises an install that cannot happen. The direction is stated; the
capability is not.

## Consequences

- **A new supply chain, with a human in it.** Every version and target is a
  reviewed catalog row. That is slower than a URL in `lsp.toml` and is the
  reason a managed install can be trusted at all.
- **Some servers will never be managed.** Their entries explain the manual
  install; those languages still get detection and the trust gate.
- **The catalog can go stale.** Caching and `--offline` are explicit, and a
  failed refresh degrades to the installed copies rather than to no servers.
- **Yanking is not remote deletion.** A yanked version stops being started once
  a fresh catalog is read; a machine that never reads the catalog keeps what it
  has. That is the honest limit of a static index.
- **Disk usage grows with versions.** Installations are immutable and
  `lsp remove <id>@<version>` is explicit; a `gc` that removes unreferenced
  versions can come later without changing the layout.
- **Windows is a second archive path.** Zip, `.exe` names and no executable bit.
  It is tested on the Windows runner, not assumed from the unix code.
- **macOS may still refuse an unsigned binary.** Gatekeeper can block a
  downloaded executable at first launch. The install verifies the bytes; it
  cannot codesign someone else's release. The docs say which servers this
  affects and what the OS prompt means, rather than teaching a bypass.
- **The signing key is a single point of failure**, as it is for extensions and
  releases. Rotation is documented and the binary trusts more than one key
  during the overlap.

## Alternatives considered

- **Download on first use, silently.** Rejected: the original non-goal, and the
  one design that turns opening a folder into executing an unreviewed binary.
- **Only detect, never install (the old non-goal).** Rejected by D12: a language
  with no package manager on the machine has no path to a working editor, and
  the status row can only apologise.
- **Trust whatever `lsp.toml` names, URL included.** Rejected: configuration
  would become a supply chain with no signature, no review and no checksum, and
  a shared profile would be a remote-code path.
- **Rely on package managers only.** Rejected as the only path: coverage is
  uneven, versions differ per distribution, and Windows has no equivalent for
  most servers. Package managers remain a valid source that detection finds.
- **Vendor every server in the release.** Rejected: hundreds of megabytes per
  platform and licences that do not permit it.
- **Ship each server as an extension pack.** Rejected as the mechanism: a pack
  can point at a program and configure it, but it has no checksum, no target
  matrix and no licence review, and ADR 0003's extension index signs a manifest,
  not an executable.
- **A live registry API.** Rejected: accounts, availability and a database to
  serve a document that changes a few times a month.
- **Auto-update managed servers.** Rejected: a new binary nobody approved,
  arriving without a command; it also breaks the pin's meaning.
- **Mirror every archive on our release storage from day one.** Not rejected on
  principle — a `mirror` field may be added for upstreams that delete assets —
  but the catalog starts by pointing at the upstream release it reviewed, so the
  bytes and the source are the same fact.
