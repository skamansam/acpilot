| CLI | <span class="pill pill--boarding">boarding</span> | `version`, `tui`, `serve`, `doctor`, `models probe`, the filesystem `ext` verbs and `secret`. The rest is the command-line phase (P5) |
| TUI | <span class="pill pill--boarding">boarding</span> | A client of the daemon that opens as an editor. `acpilot tui README.md` shows the file with no assistant pane. The pane appears only when you choose an agent from Session → Select Agent. It then has a session list, a streaming transcript, and a permission card answered with `y`/`a`/`n`. It hosts the daemon in its own process when nothing answers. It has a terminal pane over the shells an agent opened. The wheel reads back through scrollback. `F2` copy mode covers cells or whole lines, and the history stays in place while output keeps arriving. It has smart-case find, drag selection, and copy over OSC 52. Its menu bar answers `Alt` mnemonics and the mouse, and its dividers drag. `acpilot tui --demo` draws the whole shell on a seeded world. The editor pane draws a real document with syntax highlighting and a numbered gutter. The gutter markers come from the review's own patch. It also shows the current line, bracket matching, `/` find, and go-to-line. A click lands the caret, a drag selects, and `y` copies. It has `v` visual mode with `y`/`d` and a `:` command line (`:w`, `:q`), and a wheel that scrolls the view. A click focuses the tree on a row and the session list on a session. A drag held at a pane's edge scrolls past it. The widths a divider drag chose are remembered for the next start. `--no-mouse` leaves the pointer to the terminal. The footer's stats bar draws a context and a credit track per integration. `F4` names where each figure came from. A CI job holds the 200×60 drawing to a 16.7 ms frame budget |
| Text model | <span class="pill pill--boarding">boarding</span> | `acpilot-text` is the crate every editor pane will edit through. It has a character-indexed rope that keeps a file's line endings and byte-order mark. It also has selection sets with motions, edits as replacements, and an undo history that groups a typed run. `pane` adds the viewport arithmetic a renderer needs. It answers which rows are on screen and what survives the horizontal scroll (tabs and double-width characters measured in cells). It also says where the caret lands and what `/` found. Property tests cover undo-then-redo, caret bounds, offsets, and row width. The TUI's editor pane draws it |
| Syntax highlighting | <span class="pill pill--boarding">boarding</span> | `acpilot-text::highlight` has four grammars (Rust, Python, JSON, TOML) compiled in and loaded lazily. It does an incremental reparse per edit and returns spans for the visible range only, resolved to the theme's syntax tokens. A theme file therefore needs no knowledge of tree-sitter. The TUI's editor pane paints them. The desktop and web panes are P10 and P11 |
| Themes | <span class="pill pill--boarding">boarding</span> | The token schema and the two built-in themes are applied by every surface. `theme` plus `theme_tui`/`theme_gui`/`theme_web` live in the settings cascade and resolve through one `ThemeRegistry`. The TUI draws every pane from it, the desktop app takes its id from settings, and the daemon themes the page it serves. Saving a settings file recolours a running TUI. The daemon sends whole `prefs` frames on connect and after every save, so a client that watches no file still follows. A save that does not parse keeps the last good preferences and arrives as `prefs_error` |
| Desktop, web | <span class="pill pill--hangar">hangar</span> | Crates exist so the layout is real. The desktop app opens a window with the shared theme tokens, a menu bar, and the profile list. It also shows the integration stats bar (`F4` names each figure's source) and About. The daemon serves an embedded page carrying the theme's CSS variables. That page lists a directory, opens a file and saves it with `if_match`, with a diff against disk. The desktop app's panes and editor are P10 |
| Agents, sessions, permissions | <span class="pill pill--boarding">boarding</span> | Engine phase (P2). It has a manifest registry and a supervisor (stderr ring, restart, tree kill). It has sessions (initialize/new/load/prompt/cancel, numbered events). It has agent-facing file callbacks (workspace-scoped reads, writes outside it held for approval) and the permission broker (ordered rules, path globs, `allow always`, audit rows). It also has the API half. That half has `GET /v1/agents` with `available`/`missing` from `PATH`. It also has the pending list, the resolve route, and a stream that announces a new request. Terminals create, list, and attach over a WebSocket pane that replays the screen (P3-6). The `terminal/*` requests an agent makes are served by the daemon's own registry and ended with their session. A pane over each of those lets a client watch and type into the shell an agent opened. Every session appends its events and permission decisions to `session.jsonl` under the data directory, so a conversation outlives the process. No route reads a stored one back yet |
| Language servers | <span class="pill pill--hangar">hangar</span> | Language intelligence phase (P7) |
| Profiles | <span class="pill pill--hangar">hangar</span> | Profiles phase (P4) |
| Local models (LM Studio) | <span class="pill pill--boarding">boarding</span> | Models phase (P4.5). `acpilot-model` discovers models, probes capabilities and sends one chat request. `GET /v1/providers` lists declarations, and `POST /v1/providers` adds and probes one. There is no `/v1/models`, recipe or run route yet (P4.5-7), and no CLI verb |
| The model lab | <span class="pill pill--hangar">hangar</span> | Models phase (P4.5). Recipes load from `profiles/<name>/recipes/` with a last-good reload, and the run log pages and replays. No recipe route (P4.5-7) and no pane (P4.5-8) yet |
| Model-backed agents | <span class="pill pill--boarding">boarding</span> | `acpilot-agent-lm` runs a recipe as an `acp-stdio` agent: the model reaches files, terminals and permissions only through ACP callbacks. It is started by hand until promotion (P4.5-9) writes the manifest entry, and no route starts a run yet (P4.5-7) |
| Integration stats | <span class="pill pill--boarding">boarding</span> | `GET /v1/stats` lists one row per configured agent. `acpilot-stats` turns a row into a track and a sentence for every surface. The TUI draws it in the footer (`F4` names each figure's source), and the desktop app draws it in its own. The daemon serves the measured rows to the page at `/app/stats`. The sessions engine counts the context figure from the events a conversation carries. The agent's own usage update wins when it sends one. An agent with a session shows an estimated `18.4k / ?`, and one without shows nothing at all. An unknown denominator is drawn as an indeterminate track, never full or empty. No provider rows or balances yet. That is P4.5-12 |
| Panels | <span class="pill pill--boarding">boarding</span> | The TUI's window is an editor with a column either side. The Panels menu (`Alt-P`) puts the **file manager**, the **outline**, the **references** list and the **assistant** on the side a person wants. The outline lists the open buffer's definitions from the grammar it is highlighted with and re-reads them as the buffer is edited. **References** (`Shift-F12`) lists the code uses of the identifier under the caret, from `GET /v1/files/references`. The parse tree keeps comments and strings out of the list, and `Enter` opens the file at the use. Two more panels are designed and not built: a **project map** the agent writes under `.acpilot/`, and a **wiki** of linked pages per subsystem. Their shape is in [the TUI page](/acpilot/flight-deck/tui/#panels) and `TODO.md` |
| Git diff and tree | <span class="pill pill--flying">flying</span> | `acpilot-git` reads status, diffs, tree and log from the system `git`. The tree's letters and the editor's gutter are served by `GET /v1/files` and `/v1/files/list`. `GET /v1/git/status`, `/diff`, `/tree` and `/log` serve the repository itself. All three surfaces read the same routes and draw separate unstaged and staged halves of the daemon's patch. The TUI's `F6` pane and the desktop app's `F6` overlay cut it with the same `acpilot-git` helper. The browser's **Source control** panel reads only when opened. Each surface can stage one unstaged hunk through `POST /v1/git/stage-hunk`: `h`/`l` then `Shift-S` in the TUI and desktop app, **Stage hunk N of M** in the browser. It can stage the selected path through `POST /v1/git/stage` and `/unstage`: `s`/`u` in the TUI and desktop app, **Stage path**/**Unstage** in the browser. `d`/`x` (TUI and desktop) or **Discard**/**Checkout** (browser) restore the path through `/v1/git/discard` or `/v1/git/checkout`. Each arms behind a confirmation. Discard keeps staged changes, checkout resets both halves to `HEAD`, and checkout is unavailable before the first commit |
| Commit messages | <span class="pill pill--flying">flying</span> | The TUI composer opens with `c`. It drafts from the open session with `Ctrl-G` through `POST /v1/git/commit-message`, and commits the staged index with `Ctrl-S` then `y` through `POST /v1/git/commit`. The message is editable before the confirmation, and the commit route never stages: the pane's `s`/`u` prepare the index first. The desktop overlay uses the same `F6`, `s`/`u` and `c`/`Ctrl-G`/`Ctrl-S`/`y` path. `Tab`/`Shift-Tab` in its composer chooses which listed session drafts the message. The browser's panel generates a draft into an editable composer whose `Review commit` is the step before `Commit staged index`. Discard and checkout are separate confirmed actions, so a commit never silently reverts a path |

Signed index and grammar loading remain |

## How this page stays honest

The phases come from `TODO.md` in the repository, which holds the plan text. The
[ACPilot Roadmap](https://github.com/users/skamansam/projects/4) project is the
source of truth for a ticket's state: planned, in progress or shipped. When a
phase lands, its row here changes in the same pull request. A status page that
drifts is just a rumour with better typography.

<Aside type="tip" title="Why publish this at all">
Because "coming soon" is what people write when they mean "not started". A
numbered phase with a visible state is the same information without the
marketing.
</Aside>
